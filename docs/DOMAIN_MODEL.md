# Domain Model

## Status

This document defines conceptual EvalForge entities for later implementation. Milestone 4 implements the persistence layer for the entities marked below; see [Implementation Notes (Milestone 4)](#implementation-notes-milestone-4) for how each concept maps to running schema and code. Entities not listed there (experiment, variant, run, attempt, trace, span, evaluation result, metric observation, human review, adjudication, comparison, regression finding, quality gate) remain conceptual until their assigned later milestone.

## Common Rules

- Tenant boundary: every tenant-owned entity must be scoped to exactly one tenant unless explicitly documented as global configuration.
- Identity: persisted entities must have stable identities; versioned entities must also have version identities.
- Versioning: changes to evaluation-significant artifacts create new versions rather than mutating completed historical evidence.
- Mutability: completed runs, finalized snapshots, audit events, and recorded review decisions are immutable except for owner-approved correction workflows that preserve history.
- Retention: retention and deletion behavior must be tenant-scoped, auditable, and consistent with [Data Governance](DATA_GOVERNANCE.md).

## Entities

| Concept | Contract |
| --- | --- |
| Tenant | Purpose: top-level ownership and isolation boundary. Ownership: tenant administrators. Identity: stable tenant ID. Versioning rules: tenant settings may version material policy changes. Mutability or immutability: mutable membership and settings, immutable audit history. Relationships: owns workspaces, users through memberships, datasets, experiments, runs, traces, artifacts, reviews, and gates. Tenant boundary: root boundary. Lifecycle: provisioned, active, suspended, deleted. Retention considerations: tenant deletion must cover scoped data and retained audit evidence under policy. |
| Workspace or project | Purpose: organize evaluation work within a tenant. Ownership: tenant or workspace administrators. Identity: stable workspace or project ID within tenant. Versioning rules: settings changes are auditable; evaluation artifacts inside it are versioned independently. Mutability or immutability: mutable metadata, immutable historical audit events. Relationships: contains datasets, evaluation targets, experiments, runs, reviews, and gates. Tenant boundary: cannot cross tenant. Lifecycle: created, active, archived, deleted. Retention considerations: archive preserves historical evidence until retention or deletion rules apply. |
| User | Purpose: human identity that performs actions. Ownership: identity provider plus tenant membership. Identity: stable user ID and linked provider subject. Versioning rules: profile and membership changes are auditable. Mutability or immutability: mutable profile and memberships, immutable action history. Relationships: has roles, creates artifacts, performs reviews, triggers gates, administers settings. Tenant boundary: access comes through tenant membership. Lifecycle: invited, active, disabled, removed. Retention considerations: historical actions retain actor references or durable pseudonymous identifiers where required. |
| Membership | Purpose: bind a user or service identity to a tenant and, where applicable, a workspace, with an assigned role. Ownership: tenant administrators. Identity: membership ID linking user or service identity, tenant, and optional workspace. Versioning rules: role and scope changes are auditable events rather than silent updates. Mutability or immutability: mutable while active; historical membership and role-change events are immutable. Relationships: connects users and service identities to tenants, workspaces, and roles; a user's resource access is derived from membership rather than identity alone. Tenant boundary: a membership grants access to exactly one tenant and, if scoped, one workspace within it; it never grants cross-tenant access. Lifecycle: invited, active, role-changed, suspended, removed. Retention considerations: past membership and role-change history must remain reconstructable for audit even after removal. |
| Role and permission | Purpose: define allowed actions. Ownership: tenant administrators and platform policy. Identity: role ID and permission keys. Versioning rules: policy changes must be auditable and may be versioned when they affect access semantics. Mutability or immutability: role assignments are mutable; audit evidence is immutable. Relationships: assigned to users and service identities within tenant or workspace scopes. Tenant boundary: grants apply only inside authorized scope. Lifecycle: defined, assigned, changed, revoked. Retention considerations: past permissions must be reconstructable for audit. |
| Evaluation target | Purpose: identify the application or workflow being evaluated. Ownership: workspace maintainers. Identity: target ID with name and type. Versioning rules: material target configuration changes create versions or linked artifact versions. Mutability or immutability: metadata mutable; historical run references immutable. Relationships: linked to experiments, traces, workflows, models, prompts, retrieval settings, and tools. Tenant boundary: target is tenant-scoped. Lifecycle: registered, active, deprecated, archived. Retention considerations: historical targets remain explainable while dependent runs are retained. |
| Model version | Purpose: capture provider model identity and parameters. Ownership: workspace maintainers. Identity: model-version ID including provider and model identifier. Versioning rules: provider, model identifier, parameters, and assumptions require new versions when changed. Mutability or immutability: immutable once used in a completed run. Relationships: used by experiment variants, runs, evaluators, pricing, and traces. Tenant boundary: tenant-scoped unless approved as shared catalog metadata. Lifecycle: drafted, active, deprecated, archived. Retention considerations: retained with completed runs and comparisons. |
| Prompt version | Purpose: capture prompt templates and rendering rules. Ownership: workspace maintainers. Identity: prompt-version ID. Versioning rules: prompt text, variables, system instructions, rendering, or metadata changes create a new version. Mutability or immutability: immutable once snapshotted or used in completed runs. Relationships: used by targets, variants, runs, traces, and evaluators. Tenant boundary: tenant-scoped. Lifecycle: drafted, active, deprecated, archived. Retention considerations: retained while dependent evidence remains. |
| Retrieval configuration version | Purpose: capture retrieval behavior for RAG evaluation. Ownership: workspace maintainers. Identity: retrieval-config-version ID. Versioning rules: data source, index, embedding settings, filters, ranking, chunking, and top-k changes create new versions. Mutability or immutability: immutable once used in completed runs. Relationships: links to evaluation targets, variants, traces, retrieved artifacts, and metrics. Tenant boundary: tenant-scoped. Lifecycle: drafted, active, deprecated, archived. Retention considerations: retained with RAG evidence and provider limitations disclosed. |
| Tool definition version | Purpose: define callable tools and schemas. Ownership: workspace maintainers and security reviewers where required. Identity: tool-definition-version ID. Versioning rules: name, description, schema, side effects, safety classification, or execution environment changes create new versions. Mutability or immutability: immutable once used in completed runs. Relationships: used by workflows, traces, tool-call spans, and tool-use evaluators. Tenant boundary: tenant-scoped. Lifecycle: drafted, approved, active, deprecated, archived. Retention considerations: retained for trajectory and safety evidence. |
| Workflow version | Purpose: capture workflow or agent policy. Ownership: workspace maintainers. Identity: workflow-version ID. Versioning rules: step order, branching, tool policy, termination, retry, or agent policy changes create new versions. Mutability or immutability: immutable once used in completed runs. Relationships: uses prompt, model, retrieval, tool, and evaluator versions; produces runs and traces. Tenant boundary: tenant-scoped. Lifecycle: drafted, active, deprecated, archived. Retention considerations: retained with run lineage and comparisons. |
| Evaluator version | Purpose: define scoring or review behavior. Ownership: evaluation engineers. Identity: evaluator-version ID. Versioning rules: code, rule, prompt, rubric, model judge, threshold, calibration, or configuration changes create new versions. Mutability or immutability: immutable once used for recorded results. Relationships: produces evaluation results and metric observations; may use model versions or rubric versions. Tenant boundary: tenant-scoped unless explicitly shared as catalog metadata. Lifecycle: drafted, calibrated, active, deprecated, archived. Retention considerations: retained with all results it produced. |
| Pricing version | Purpose: capture cost assumptions. Ownership: platform or workspace maintainers. Identity: pricing-version ID with provider, unit, currency, and effective interval. Versioning rules: rate, unit, currency, or effective date changes create new versions. Mutability or immutability: immutable once used in completed cost calculations. Relationships: used by runs, spans, metric observations, comparisons, and gates. Tenant boundary: tenant-scoped or global catalog with tenant-scoped use. Lifecycle: drafted, active, superseded, archived. Retention considerations: retained for historical cost explanation. |
| Dataset | Purpose: group test cases for evaluation. Ownership: workspace maintainers. Identity: dataset ID. Versioning rules: dataset content changes create dataset versions or snapshots. Mutability or immutability: dataset metadata mutable; finalized snapshots immutable. Relationships: contains test cases and snapshots; used by experiments. Tenant boundary: tenant-scoped. Lifecycle: created, edited, snapshotted, archived, deleted. Retention considerations: deletion must account for snapshots used in completed runs. |
| Dataset version or immutable snapshot | Purpose: freeze dataset membership and content for reproducible execution. Ownership: workspace maintainers. Identity: snapshot ID and content hash. Versioning rules: every finalized snapshot is a new immutable version. Mutability or immutability: immutable after finalization. Relationships: references dataset and test-case versions; used by experiments and runs. Tenant boundary: tenant-scoped. Lifecycle: drafted, finalized, used, archived. Retention considerations: retained while dependent runs, results, or gates are retained. |
| Test case | Purpose: define an evaluation input, expected references, metadata, and labels. Ownership: workspace maintainers. Identity: test-case ID and version ID. Versioning rules: input, reference, metadata, or expected behavior changes create new versions. Mutability or immutability: editable before snapshot; immutable within finalized snapshot. Relationships: belongs to datasets and snapshots; produces run attempts and evaluation results. Tenant boundary: tenant-scoped. Lifecycle: created, revised, snapshotted, archived, deleted subject to retention. Retention considerations: sensitive content must follow tenant retention and deletion policy. |
| Experiment | Purpose: define a planned comparison or evaluation. Ownership: workspace maintainers. Identity: experiment ID. Versioning rules: material changes create a new experiment revision or derivative experiment. Mutability or immutability: draft mutable; launched definition immutable for completed runs. Relationships: references target, dataset snapshot, variants, evaluators, metrics, repetitions, and gates. Tenant boundary: tenant-scoped. Lifecycle: drafted, launched, running, completed, archived. Retention considerations: retained with results and audit history. |
| Experiment variant | Purpose: represent one compared configuration. Ownership: experiment owner. Identity: variant ID within experiment. Versioning rules: references immutable artifact versions rather than mutable settings. Mutability or immutability: immutable after launch. Relationships: points to model, prompt, retrieval, tool, workflow, evaluator, and pricing versions; produces runs. Tenant boundary: tenant-scoped through experiment. Lifecycle: drafted, launched, completed, archived. Retention considerations: retained for comparison lineage. |
| Run | Purpose: represent execution of an experiment variant against a dataset snapshot. Ownership: experiment owner and executing service identity. Identity: run ID. Versioning rules: completed run snapshot is immutable; reruns create new runs. Mutability or immutability: state mutable until terminal; immutable after completion. Relationships: has attempts, traces, artifacts, results, metric observations, and costs. Tenant boundary: tenant-scoped. Lifecycle: queued, running, completed, failed, canceled. Retention considerations: retained while needed for evidence, gates, and audit. |
| Attempt | Purpose: represent a single execution try for a run or test case. Ownership: executing service identity. Identity: attempt ID with repetition index when applicable. Versioning rules: attempts record exact inputs and execution metadata. Mutability or immutability: immutable after terminal state. Relationships: belongs to run and test case; has trace, spans, artifacts, errors, and observations. Tenant boundary: tenant-scoped through run. Lifecycle: queued, running, succeeded, failed, canceled. Retention considerations: retained as diagnostic evidence. |
| Trace | Purpose: capture end-to-end execution evidence. Ownership: run owner or ingestion source. Identity: trace ID. Versioning rules: canonical trace schema may version; recorded trace instances are immutable after finalization. Mutability or immutability: appendable during active ingestion, immutable after finalization. Relationships: contains spans and artifacts; links to attempts, runs, targets, and evaluations. Tenant boundary: tenant-scoped. Lifecycle: ingested, processing, finalized, archived. Retention considerations: sensitive trace data may need redaction, retention, or deletion. |
| Span | Purpose: capture a timed operation inside a trace. Ownership: trace owner. Identity: span ID within trace. Versioning rules: schema versions capture span semantics. Mutability or immutability: immutable after finalization. Relationships: belongs to trace; may reference model calls, retrieval calls, tool calls, artifacts, costs, and errors. Tenant boundary: tenant-scoped through trace. Lifecycle: created, finalized, archived. Retention considerations: may contain sensitive inputs or outputs subject to governance. |
| Artifact | Purpose: store supporting content such as prompts, completions, files, retrieved context, tool outputs, reports, and exports. Ownership: tenant or workspace owner. Identity: artifact ID with hash and media metadata. Versioning rules: content changes create new artifacts or versions. Mutability or immutability: immutable once referenced by completed evidence. Relationships: linked to datasets, traces, runs, results, reviews, and exports. Tenant boundary: tenant-scoped. Lifecycle: uploaded, validated, referenced, archived, deleted. Retention considerations: subject to classification, redaction, storage, and deletion rules. |
| Evaluation result | Purpose: record evaluator output for a run, attempt, test case, or artifact. Ownership: evaluator execution identity. Identity: result ID. Versioning rules: bound to evaluator version and input evidence; recomputation creates new result. Mutability or immutability: immutable after recorded, except superseded by new result. Relationships: has metric observations and links to evaluator, run, attempt, test case, and artifacts. Tenant boundary: tenant-scoped. Lifecycle: pending, produced, invalidated by new run, archived. Retention considerations: retained with source evidence and comparisons. |
| Metric observation | Purpose: store raw or normalized measurement used for scoring and aggregation. Ownership: evaluator or measurement service. Identity: observation ID. Versioning rules: bound to metric definition, evaluator version, and source evidence. Mutability or immutability: immutable after recorded. Relationships: belongs to evaluation result or run; aggregated into comparisons and gates. Tenant boundary: tenant-scoped. Lifecycle: captured, aggregated, archived. Retention considerations: retained for auditability of aggregate values. |
| Human review | Purpose: capture reviewer assessment under a rubric. Ownership: assigned reviewer and review workflow owner. Identity: review ID. Versioning rules: rubric changes create new rubric or evaluator versions; review records keep the version used. Mutability or immutability: submitted review is immutable, with corrections recorded as new events. Relationships: references run, test case, artifact, rubric, reviewer, adjudication, and metric observations. Tenant boundary: tenant-scoped. Lifecycle: assigned, in review, submitted, adjudicated, archived. Retention considerations: reviewer comments may contain sensitive content. |
| Adjudication | Purpose: resolve review disagreement or deployment-blocking review decisions. Ownership: authorized adjudicator. Identity: adjudication ID. Versioning rules: bound to review set and rubric version. Mutability or immutability: immutable after decision, with later corrections audited. Relationships: references reviews, evidence, final decision, and gate impact. Tenant boundary: tenant-scoped. Lifecycle: opened, decided, closed. Retention considerations: retained for gate and audit evidence. |
| Comparison | Purpose: compare variants, baselines, runs, or evaluator outputs. Ownership: experiment owner or analysis service. Identity: comparison ID. Versioning rules: comparison inputs and aggregation configuration are versioned or immutable references. Mutability or immutability: immutable after publication; rerun creates new comparison. Relationships: references experiments, variants, metrics, regression findings, and gates. Tenant boundary: tenant-scoped. Lifecycle: requested, calculated, published, archived. Retention considerations: retained while used for decisions. |
| Regression finding | Purpose: record a quality, safety, latency, or cost degradation. Ownership: analysis service and experiment owner. Identity: regression-finding ID. Versioning rules: tied to comparison version and metric definitions. Mutability or immutability: immutable finding evidence; status may change with audit. Relationships: belongs to comparison; may trigger quality gates and review. Tenant boundary: tenant-scoped. Lifecycle: detected, triaged, accepted, resolved, waived. Retention considerations: retained for release history and audit. |
| Quality gate | Purpose: define and record deployment or acceptance criteria. Ownership: workspace maintainers and authorized approvers. Identity: gate ID and gate-decision ID. Versioning rules: gate definitions version; decisions bind to definition version and evidence. Mutability or immutability: definitions mutable through versions; decisions immutable except audited overrides. Relationships: uses comparisons, metrics, reviews, and regression findings; integrates with CI/CD in later milestones. Tenant boundary: tenant-scoped. Lifecycle: drafted, active, evaluated, passed, failed, overridden, archived. Retention considerations: decisions retained as release evidence. |
| Audit event | Purpose: record security, data, review, and gate actions. Ownership: platform audit subsystem. Identity: audit-event ID with timestamp and actor. Versioning rules: event schema may version; event content is append-only. Mutability or immutability: immutable append-only record. Relationships: references tenant, actor, resource, action, outcome, and request context. Tenant boundary: tenant-scoped for access, with administrative review controls. Lifecycle: emitted, retained, exported under authorization, expired under policy. Retention considerations: retention may outlive deleted resources when legally or operationally required. |

## Relationship Summary

A tenant contains workspaces or projects. Workspaces contain evaluation targets, datasets, experiments, and quality gates. Datasets contain versioned test cases and immutable snapshots. Experiments compare variants that reference versioned prompts, models, retrieval configurations, tool definitions, workflows, evaluators, and pricing definitions. Runs and attempts produce traces, spans, artifacts, evaluation results, metric observations, comparisons, regression findings, human reviews, adjudications, quality-gate decisions, and audit events.

## Implementation Notes (Milestone 4)

- **Workspace or project**: `workspaces` table (migration `20260815_0003_eval_domain_resources.py`), tenant-scoped, `UNIQUE (tenant_id, slug)`. Workspace-scoped authorization does not exist yet (see [Tenancy and Authorization](TENANCY_AND_AUTHORIZATION.md)), so creation is a tenant-level action (`TenantAction.CREATE_WORKSPACE`, `tenant_admin` only) — the standard role fills in for the not-yet-implemented workspace-administrator role.
- **Evaluation target**: `evaluation_targets` table, tenant- and workspace-scoped via a composite `(workspace_id, tenant_id)` foreign key.
- **Model version, prompt version, retrieval configuration version, tool definition version, workflow version, evaluator version, pricing version**: these seven concepts share identical versioning mechanics (stable logical resource, immutable content-hashed versions, explicit derivation lineage) and differ only in the JSON shape of their content, so Milestone 4 represents them uniformly as `versioned_resources` (logical identity) and `versioned_resource_versions` (immutable version identity) tables, discriminated by `evalforge_api.domain.evaluation_enums.ResourceKind`. This is a persistence-layer modeling choice, not a change to the underlying domain concepts — each kind keeps its own name and content shape at the domain and application layers (`evalforge_api.application.versioned_resource_service`).
- **Dataset**: `datasets` table, tenant- and workspace-scoped.
- **Test case**: `test_cases` (logical identity) and `test_case_versions` (immutable content-hashed versions) tables. "Editable before snapshot" is implemented as always creating a new version — no supported path rewrites an existing version's content.
- **Dataset version or immutable snapshot**: `dataset_snapshots` (identity, status, content hash) and `dataset_snapshot_items` (frozen membership, one row per included test-case version with an explicit `sequence_index` for deterministic ordering) tables. A `BEFORE INSERT` trigger on `dataset_snapshot_items` rejects membership changes once the parent snapshot's status is no longer `draft` and rejects a test-case version that does not belong to the snapshot's own dataset; a `BEFORE UPDATE` trigger on `dataset_snapshots` rejects any further change once `status = 'finalized'`. The snapshot content hash covers the frozen `(test_case_id, test_case_version_id, version_number, content_hash)` membership list, so it changes if and only if frozen content changes.
- **Artifact**: `artifacts` (logical identity and metadata) and `artifact_versions` (immutable content hash, byte size, content type, and tenant-scoped object-storage key) tables. Bytes are stored via `evalforge_api.adapters.artifact_object_storage.S3ArtifactObjectStorage`; PostgreSQL never stores artifact bytes directly.
- **Identity and version identity**: every versioned table separates a logical-resource row (stable UUID) from version rows (separate stable UUID plus a per-resource sequential `version_number`); no supported application or database path updates an existing version row's content.
- **Lineage**: represented with explicit relational references, not opaque JSON — composite `(id, tenant_id)` foreign keys throughout (see [Tenancy and Authorization](TENANCY_AND_AUTHORIZATION.md)) make a cross-tenant lineage reference impossible to insert, and self-referential `derived_from_version_id` / `derived_from_artifact_version_id` columns record explicit derivation chains within one logical resource or artifact (`evalforge_api.application.lineage_service`).
- **Hashing**: SHA-256 over canonicalized JSON (`evalforge_api.domain.hashing`, sorted keys, fixed separators, ASCII-escaped) for structured content, and SHA-256 over raw bytes for artifacts. The algorithm and a canonicalization-version tag are recorded alongside every hash.
- **Retention**: `retention_class` (`standard` / `extended` / `legal_hold`), `retain_until`, and `archived_at` columns exist on every immutable-evidence table; Milestone 4 captures this metadata but does not implement retention or deletion execution (see [Data Governance](DATA_GOVERNANCE.md)).
